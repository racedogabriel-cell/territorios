# Supabase

Access sigue siendo la fuente principal. Supabase queda como puente web para publicar los datos semanales y recibir acciones de colaboradores desde la pagina estatica.

## Arquitectura recomendada

- Access y `servir.ps1`: fuente principal y aplicacion local de administracion.
- Supabase: replica web de `datos_semana` y almacen de acciones pendientes en `acciones_colaboradores`.
- Netlify u otro hosting estatico: `predicacion-netlify.html`, `mapa-semanal.html`, `supabase.js`, `mapa.svg`, `mapa_meta.json`. El estado del mapa semanal va en Supabase (`datos_semana.mapaSemanal`), no en JSON estatico.
- Sin Supabase no hay flujo web para cargar datos ni guardar cierres; no queda cola JSON ni archivo intermedio en el navegador para ese fin.

No hace falta desafectar Netlify para que el sistema sea simple. La pagina ya es estatica; moverla a otro hosting no reduce la logica. Lo importante es depender solo de Supabase para datos web y acciones, sin JSON manual.

## Tablas

### `datos_semana`

Formato: la columna `datos` guarda el **objeto del paquete semanal** (`exportado`, `version`, `salidas`, `responsables`, `territorios`). Ver definición actual en `sql/create_tables.sql`.

- **`canal`**: texto único por fila. La publicación oficial para Netlify usa `canal = 'publica'` y se actualiza con **UPSERT** (PostgREST `on_conflict=canal`) desde `mapa.html` o desde código que llame a `TerritoriosSupabase.upsertDatosSemana(bundle)`.
- Si tu base ya existía **sin** columna `canal`, ejecutá una vez `sql/alter_datos_semana_canal_upsert.sql` en el SQL Editor.

El campo `datos` debe contener, como mínimo:

```json
{
  "exportado": "2026-05-15T00:00:00.000Z",
  "version": 2,
  "salidas": [],
  "responsables": [],
  "territorios": []
}
```

La página también acepta filas cuyo JSON normalizado venga solo en columnas legacy; lo habitual es el objeto anterior en `datos`.

### `acciones_colaboradores`

```sql
create table acciones_colaboradores (
  id bigint generated by default as identity primary key,
  tipo text not null,
  payload jsonb not null,
  origen text not null default 'predicacion-netlify',
  procesado boolean not null default false,
  creado_en timestamptz not null default now(),
  procesado_en timestamptz
);
```

## Politicas RLS sugeridas

La ANON KEY es publica. Con RLS activo, el proyecto incluye politicas para `anon` que permiten:

- `datos_semana`: **select**, **insert**, **update** (necesario para UPSERT del boton en mapa y para mantener una fila `publica`).
- `acciones_colaboradores`: **insert**, **select**, **update**, **delete** solo cuando `procesado = false` (la pagina puede eliminar o reemplazar pendientes; **delete** de filas ya procesadas queda restringido o solo con `service_role` segun tu politica).

En entornos mas restrictivos podrias limitar insert/update en `datos_semana` a una **service_role** y exponer un backend propio; el flujo actual prioriza simplicidad desde la PC con `servir.ps1`.

## Acciones pendientes en `predicacion-netlify.html`

La pagina estatica usa **solo Supabase** para datos semanales y para las acciones de colaboradores.

1. Tras cargar `datos_semana`, pide a PostgREST las filas de `acciones_colaboradores` con `procesado = eq.false` (`TerritoriosSupabase.listarAccionesPendientes`).
2. Por cada **numero de territorio** se conserva una sola accion relevante: si hay varias en Supabase, la mas reciente por `creado_en`.
3. Esa fusion **no reemplaza** el snapshot publicado en `datos_semana`: solo ajusta la vista (tooltip, estilo `pendiente-sync`, manzanas pendientes, etc.) hasta que `datos_semana` se vuelva a publicar o Access aplique el cierre.
4. Si ya hay una accion pendiente en Supabase para ese territorio, los nuevos envios hacen **PATCH** (`actualizarAccion`) en lugar de **INSERT**.
5. El modal del territorio permite **eliminar** la fila pendiente (`eliminarAccion`) antes del sync. Eso exige una politica RLS que permita **DELETE** al rol `anon` **solo** con `procesado = false` (en proyectos nuevos esta en `sql/create_tables.sql`; en bases antiguas ejecuta `sql/alter_acciones_delete_anon.sql`).
6. Sin red o con Supabase indisponible, la pagina no puede guardar acciones nuevas ni recargar datos; permanece la ultima vista cargada con exito en esa sesion.

## Flujo de uso

1. Desde Access (o desde **mapa.html**, boton **Enviar a Supabase**) se publica el paquete semanal en `datos_semana` (fila `canal = publica`). Para traer lo ultimo de Supabase a Access desde el mapa, usar **Recibir de Supabase**.
2. La pagina Netlify carga desde Supabase (ultimo `exportado`).
3. Si la pagina se abre en la misma PC/red con `servir.ps1`, las acciones se aplican directo en Access.
4. Si no hay servidor local, las acciones se insertan o actualizan en `acciones_colaboradores` mediante Supabase.
5. Si Supabase no responde, la accion **no** se encola en el navegador: el usuario ve un error y debe reintentar cuando haya conexion.
6. En la PC principal se ejecuta `Sync-SupabaseToAccess.ps1` para importar a Access y marcar los registros como procesados.

La pagina Netlify (`TerritoriosSupabase` en `Netlify/supabase.js`) expone tambien `listarAccionesPendientes`, `actualizarAccion` y `eliminarAccion` para esta vista y edicion de pendientes.

## Publicar desde mapa.html

Con `servir.ps1` en marcha y la base Access actualizada:

1. Abrí `http://localhost:8080/mapa.html` (o la URL que uses).
2. Configurá **una sola vez** `SUPABASE_URL` y `SUPABASE_ANON_KEY` en `Netlify/supabase.js` (mismos valores que en Netlify).
3. En Supabase, asegurate de tener la tabla `datos_semana` con columna **`canal`** unica y politicas **insert/update** para `anon` (ver `sql/create_tables.sql` o `sql/alter_datos_semana_canal_upsert.sql`).
4. **Enviar a Supabase**: arma el bundle desde `/api/salidas` y catalogos (equivalente al paquete semanal de `predicacion.html`) y hace **UPSERT** en `datos_semana` (`canal = publica`).
5. Mensajes en pantalla junto al boton: *Enviando...* / *Enviado correctamente* / *Error al enviar* (detalle en `alert`).
6. La pagina publica (`predicacion-netlify.html`) mostrara los datos nuevos al pulsar **Actualizar** (segun orden `exportado`).

### Error: «Could not find the 'canal' column … schema cache»

Significa que en tu proyecto Supabase la tabla `datos_semana` **no tiene la columna** `canal` (no ejecutaste la migración), o PostgREST aún no refrescó el esquema.

1. En **Supabase Dashboard** → **SQL Editor**, ejecutá el contenido completo de **`sql/alter_datos_semana_canal_upsert.sql`** (una vez).
2. El script incluye `NOTIFY pgrst, 'reload schema'` para refrescar la API; si igual falla, esperá **1–2 minutos** y tocá de nuevo **Enviar a Supabase**.
3. Comprobación rápida en SQL Editor: `select canal from public.datos_semana limit 1;` — debe existir la columna y tener valores.

## Sincronizar hacia Access

Primero iniciar el servidor local:

```powershell
.\servir.ps1
```

Luego, en otra terminal:

```powershell
.\Sync-SupabaseToAccess.ps1
```

El script descarga registros con `procesado = false`, llama a `http://localhost:8080/api/importar-cierres-colaborador` y marca como procesados solo si la importacion local responde correctamente.

## Archivos modificados

- `Netlify/supabase.js`: cliente REST (`cargarDatosSemana`, `guardarAccion`, `listarAccionesPendientes`, `actualizarAccion`, `eliminarAccion`, `upsertDatosSemana`).
- `mapa.html`: botones **Recibir de Supabase** y **Enviar a Supabase** (requieren `servir.ps1` y `Netlify/supabase.js` configurado).
- `Netlify/predicacion-netlify.html`: carga `datos_semana`, fusiona acciones pendientes solo desde Supabase y guarda acciones con POST/PATCH en `acciones_colaboradores`.
- `sql/create_tables.sql`, `sql/alter_datos_semana_canal_upsert.sql`, `sql/alter_acciones_delete_anon.sql`: esquema y migraciones.
- `Sync-SupabaseToAccess.ps1`: sincronizacion Supabase -> Access.
- `SUPABASE.md`: esta documentacion.
